### 1.2 P-2 git 管理范围与使用时机（已裁决 2026-09-15）

- **背景**：指南 4.6 只定义了 commit（3.4 出口）与 tag（3.6 门禁后）两个写入时点，但"触及清单 = diff 边界""验证隔离""基线能力"等核心机制隐含更多 git 介入需求。
- **验收标准**：讨论有明确结论，并落到指南 `references/git.md` 与 skill 层对应小节。
- **状态**：已裁决（指南层已落地；skill 层同步待执行）。
- **裁决结果**：
  1. **存留边界**：唯一事实必存（工件源码、`CHANGELOG.md`、`evals/`、`iterations/` 留痕）；可再生的不存（`results/` 基线物理存在但 `.gitignore` 忽略）；03 脱敏对照表因敏感不入库、由人 commit 时裁决剥离。
  2. **写/读分治**：git 写操作（init、commit、tag、changelog、rollback）交人执行，skill 只负责在守卫点提醒；git 读操作（archive、diff、log）由 skill 自动执行。提醒必须携带冻结语义（3.4 commit 是 3.4→3.5 的守卫）。
  3. **操作时机**：init（启动）→ commit 候选（3.4 出口，冻结）→ archive（3.5 验证）→ tag + 留痕/changelog commit（3.6 发布）→ rollback（生产恶化）；每轮最少 2 个 commit（候选 + 归档）。
  4. **落地**：指南新增 `docs/guide/references/git.md` 为权威规范，并清除指南内 git 机制残留（只留状态机语义）；skill 层同步「写交人 + 提醒」到 `SKILL.md` 与 `references/04`、`06`（待执行）。

### 1.4 P-4 迭代进度可见性与状态推导（讨论中）

- **背景**：「文件即进度」设计下，状态从任务目录文件推导（state_check.py），存在五个缺口：
  ①无「当前活动任务」指针——多任务目录并存时只取最大编号，区分不了推进中 / 搁置 / 人工澄清等待态；
  ②plan.md 与 iterations/ 链接单向——P-x 转任务后条目未登记 T-xxx，反查靠全文搜索；
  ③无一眼聚合视图——「哪个任务 + 哪一步 + 卡在哪」需人工拼合；
  ④**裁决豁免无机制**——人工裁决跳过的状态（如 T-001 跳过 3.3）在文件链模型中无表达，文件链强制存在与跳过裁决冲突，执行者只剩「补写文件（守卫博弈）」或「卡死」两条路；
  ⑤**state_check.py 判定盲区**——只看文件不看 git（候选是否已 commit 不可见），且对跳跃文件链（01 缺失但 04 存在）误报「3.1 归因中」而非给出可用状态。
- **触发事件**：a) 2026-09-15 维护者反馈「没有一个持久化文件让程序或人直接看到走到了哪一步」；b) 2026-09-15 T-001 事故——执行 agent 试图走完全流程、擅自补写文件链、未按规约使用 state_check.py 而直接读文件、未解释「候选/git archive 副本」语义即执行，被维护者回滚。归因：Agent 执行问题（守卫博弈、越权、沟通失败）+ 工件设计问题（缺口 ④⑤）。
- **已定方向（2026-09-15 讨论共识）**：状态从工件推导，不建「当前 state」持久文件（第二事实源必漂移——反例：P-2 状态行「skill 层同步待执行」在人提交后即过时）；已终态条目（已裁决/已关闭）可挪 plan.md 归档区，无漂移风险。
- **验收标准**：①一个命令回答「活动任务是哪个、各任务什么状态、哪些在等人、候选提交了没」；②状态判定 100% 从既有工件（含 git）推导，无独立状态存储；③plan.md ↔ iterations/ 双向可查；④被裁决跳过的状态有合法表达，文件链缺口不得由执行 agent 擅自补写；⑤跳跃文件链不误报状态。
- **状态**：讨论中（方案讨论进行中）。
