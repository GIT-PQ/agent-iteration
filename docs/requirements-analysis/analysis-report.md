## 2. 问题定义

### USP 分析

| 维度 | 内容 |
|---|---|
| User（谁） | Skill 的开发和维护人员 |
| Situation（场景） | Skill 交付后，业务测试通过反馈表单提交问题（含错误案例的 Input、问题描述、正确答案），开发人员需要据此升级迭代 Skill |
| Problem（问题） | 没有统一的迭代流程和方法论，靠个人经验摸索着改，迭代质量取决于个人能力，参差不齐；流程在心中未显性化，每步该做什么、产出什么、怎么判断做对了没有标准 |

### JTBD 核心任务

| 维度 | 内容 |
|---|---|
| 核心执行者 | Skill 开发维护人员 |
| 核心任务 | 在业务反馈问题后，按照一套标准化的迭代流程完成问题分析、修复和回归验证，以确保迭代质量不依赖个人经验 |
| 任务边界 | 覆盖：从拿到业务反馈表单→到回归测试通过交付；不覆盖：业务测试本身、Skill 的初始开发 |

### IPO 任务分析

| 维度 | 内容 |
|---|---|
| Output（输出） | O1: 修复后的新版本 Skill；O2: 回归测试通过；O3: 迭代过程文档（变更记录、根因分析、经验沉淀） |
| Input（输入） | I1: 原始 Skill 文件；I2: 业务反馈表单；I3: 错误案例的 Input；I4: 原始测试用例/案例集；I5: Skill 原始设计文档；I6: 历史迭代记录 |
| Process（过程） | P1: 接收反馈 → P2: 问题归因 → P3: 变更设计 → P4: 生成测试 → P5: 变更实现 → P6: 验证 → P7: 发布（P2~P5 为核心缺口，靠个人经验无标准） |

### 事实与方案剥离

| 类别 | 内容 |
|---|---|
| 客观事实 | ① Skill 交付后有业务测试反馈环节，反馈通过结构化表单提交；② 反馈表单含日期、记录人、模块、问题描述、正确答案等字段；③ 业务只提供错误案例的 Input 部分；④ 开发人员可获取原始 Skill、测试用例、设计文档、历史迭代记录；⑤ 当前迭代完成标准：新问题修复 + 回归测试通过；⑥ 迭代过程需要文档类产物；⑦ 用户心中已有7步流程但未显性化 |
| 主观表述 | ① "缺乏一套方法论"；② "不知道该如何迭代"；③ "不知道中间产物" |
| 方案设想 | ① 需求名称"迭代 Skill 的 Skill"暗示要做一个 Skill/Agent 来指导迭代；② 用户描述的7步流程本身就是一个方案方向 |
| 待验证判断 | ① P2~P5 是核心缺口（从描述推断，但未验证 P1/P6/P7 是否也有问题）；② 流程显性化后开发人员会愿意采用；③ 每一步的方法论可以被标准化 |

### 初步关键假设

| # | 假设名称 | 类型 | 说明 | 不成立后果 |
|---|---|---|---|---|
| H1 | 流程缺口假设 | 问题假设 | 核心问题是 P2~P5 缺乏方法论和中间产物，P1/P6/P7 基本可用 | 如果 P1/P6/P7 也有问题，流程范围需要扩大 |
| H2 | 标准化可行性假设 | 可行性假设 | P2~P5 的每一步可以被标准化为可执行的方法论 | 如果某些步骤高度依赖创造性判断，难以标准化，则 Agent 能做的有限 |
| H3 | Agent 适用性假设 | 可行性假设 | AI Agent 适合承担"指导迭代流程"的角色，而非仅做文档模板 | 如果 Agent 只能做模板填充，价值可能不如一份 SOP 文档 |
| H4 | 采纳意愿假设 | 推广假设 | 开发人员愿意按照标准化流程进行迭代，而非继续凭经验 | 如果开发人员不采用，流程和 Agent 形同虚设 |
| H5 | 反馈质量假设 | 输入假设 | 业务反馈表单的信息足够支撑问题归因和变更设计 | 如果反馈质量不足，P2 归因步骤无法有效执行 |
| H6 | 迭代频率假设 | 场景假设 | Skill 迭代发生频率足够高，值得投入做标准化 | 如果迭代很少发生，做一套标准化方法的 ROI 不足 |

### 缺失信息

- 迭代发生的实际频率（多久一次）
- 反馈表单中"问题转义/本质问题"字段是否稳定填写
- P1/P6/P7 步骤是否也存在问题
- 是否确认要做成一个 AI Agent/Skill（而非一份 SOP 文档）

## 3. 关键场景与机会点

### 核心执行者

Skill 开发维护人员（协作方：业务测试人员、产品、业务）

### 替代方案分析

| 方式 | 当前体验 | 不足之处 |
|---|---|---|
| 靠个人经验摸索着改，脑中有分析思路但未显性化 | 能改但心里没底，不同人质量差异大 | 流程未固化、经验未沉淀、无法跨人跨次复用 |

### 任务地图与 APO 分析

| 阶段 | Action | Pain | Opportunity | 重要性 | 满意度 | 机会类型 |
|---|---|---|---|---|---|---|
| P1 接收反馈 | 阅读反馈表单，提取问题描述 | 反馈质量参差不齐 | 建立接收标准，自动补全提示 | 中 | 中 | 潜在机会 |
| P2 问题归因 | 根据错误案例分析根因 | 没有归因方法，依赖个人经验 | 提供归因框架和检查清单 | 高 | 低 | 🔴 核心机会 |
| P3 变更设计 | 根据归因设计修改方案 | 不同 Skill 类型差异大，经验无法复用，缺少 SOP 沉淀 | 提供设计框架 + 经验检索 | 高 | 低 | 🔴 核心机会 |
| P4 生成测试 | 构造测试用例 | 不知道覆盖哪些场景，凭感觉 | 提供测试模板和覆盖度检查 | 高 | 低 | 🔴 核心机会 |
| P5 变更实现 | 修改 Skill 代码 | 改动范围控制不住 | 提供变更范围检查和影响分析 | 高 | 低 | 🔴 核心机会 |
| P6 验证 | 执行回归测试 | 有回归但标准不明确 | 明确验证标准 | 中 | 中 | 潜在机会 |
| P7 发布 | 发布新版本 | 不确定是否需要评审 | 建立发布前检查清单 | 低 | 中 | 低价值 |

### 核心机会

- **P2 问题归因**：缺乏归因方法和框架
- **P3 变更设计**：不同 Skill 类型问题差异大，经验无法跨类型复用，缺少 SOP 分享和沉淀
- **P4 生成测试**：测试覆盖凭感觉
- **P5 变更实现**：变更范围控制不住

### 隐藏洞察

| 维度 | 内容 |
|---|---|
| 推力 | 每次迭代从零开始分析，经验无法复用，改完没有沉淀 |
| 拉力 | 一套适配不同 Skill 类型的框架 + 经验积累机制可减少重复劳动 |
| 习惯 | "具体问题具体分析"本身是习惯，觉得不需要框架，觉得"没法统一" |
| 焦虑 | 标准化会不会限制灵活性？一套 SOP 能覆盖不同类型吗？做出来会不会不实用？ |

**核心矛盾**：不同 Skill 类型的问题差异大（多样性高），但迭代流程是相同的（7步）→ 需要标准化的不是"怎么解决问题"，而是"怎么走好迭代的每一步"

### 需求假设

| # | 假设名称 | 类型 | 等级 | 说明 | 待验证原因 |
|---|---|---|---|---|---|
| RH1 | 流程框架需求假设 | 价值假设 | A | 开发人员需要每一步"该做什么、产出什么、怎么判断做对了"的具体指导 | 需验证显性化后是否真的有用 |
| RH2 | 跨类型适应性假设 | 可行性假设 | A | 不同 Skill 类型问题差异大，但迭代流程可抽象为通用框架 | 需验证框架能否适配不同类型 |
| RH3 | 经验沉淀需求假设 | 价值假设 | A | 迭代经验无法跨人跨次复用，需要经验沉淀和分享机制 | 需验证开发人员是否愿意花时间沉淀 |
| RH4 | 协作沟通需求假设 | 场景假设 | B | 与测试、业务、产品三方协作需要标准化沟通确认机制 | 协作痛点具体在哪未明确 |
| RH5 | 反馈质量依赖假设 | 输入假设 | B | P2 归因依赖反馈表单质量，"问题转义"字段可能未填 | 待补信息 |
| RH6 | Agent 定位假设 | 可行性假设 | A | Agent 价值应定位为"迭代流程引导 + 经验检索"，而非"自动解决问题" | 问题多样性意味着 Agent 无法直接解决问题 |

### 关键风险点

- 不同 Skill 类型问题差异大，标准化框架可能无法覆盖所有场景（RH2）
- Agent 可能只能做流程引导和模板填充，价值不如一份好的 SOP 文档（RH6/H3）
- 开发人员可能不愿意按标准化流程走（H4）
- 反馈表单质量不稳定，影响归因效果（RH5/H5）

## 4. 需求评估结果

### 评估三角形

| 维度 | 判断 | 依据 |
|---|---|---|
| 刚性 | 中偏强 | 不解决不会业务中断，但影响业务对智能体部门的信任，浪费多方时间，迭代质量参差不齐，代价持续累积 |
| 频次 | 中高频 | 做 Skill 就必然需要迭代，反馈定期到来但问题数量不固定，稳定持续型 |
| 普遍性 | 高 | 部门 10+ 人全员受影响，非个案 |

### 风险评估

| 风险类型 | 描述 | 严重程度 | 应对建议 |
|---|---|---|---|
| 技术/可行性风险 | 不同 Skill 类型问题差异大，框架太抽象则不实用，太具体则无法泛化 | 高 | 先从 1-2 个 Skill 类型试点，验证可适配性后再推广 |
| 采纳风险 | 开发人员可能认为标准化流程是额外负担 | 中 | 框架轻量、嵌入现有流程；优先解决最痛环节让用户感受到价值 |

### 核心机会对比

| 维度 | P2 问题归因 | P3 变更设计 | P4 生成测试 | P5 变更实现 |
|---|---|---|---|---|
| 业务价值 | 高 | **最高** | 中 | 中 |
| 标准化可行性 | 中 | **最低** | 中高 | 中高 |
| Agent 适用性 | 中高 | **中低** | 高 | 中 |
| 建议切入顺序 | 🥇 第一切入 | ❌ 不建议 MVP | 🥈 第二切入 | 🥉 第三切入 |

### 优先级建议

| 优先级 | 理由 |
|---|---|
| **P1（建议推进）** | ①问题真实，全员持续遇到；②影响超出效率，涉及部门信任；③有明确 MVP 切入点（P2 归因 + P4 生成测试）；④适合训战营孵化（边界清晰、输入输出明确）；⑤P3 虽最痛但可行性最低，不建议作为 MVP 切入 |

### 是否建议进入下一阶段

否 — 轻量路径，跳过算阶段，直接进入汇总

## 6. 产品内核前置判断

| 维度 | 判断 |
|---|---|
| 最小价值单元 | 拿到一个业务反馈问题后，引导开发人员按标准步骤完成问题归因，并产出归因文档 |
| 用户选择理由 | 当前靠个人经验改心里没底，工具提供掌控感和确认感——从哪个角度分析、分析到什么程度算够 |
| 不可替代价值 | 如果拿掉"归因引导"只保留"流程模板"，用户可能不买单——流程模板心里已有，缺的是每一步怎么做的具体指导 |
| 机会点清晰度 | 中等——核心矛盾已识别，但"迭代流程引导+经验检索"定位仍偏宽泛，需在MVP阶段进一步聚焦 |
| 贪大求全风险 | 中高风险——7步全覆盖是诱惑，但P3可行性最低。建议MVP只做P2+P4 |
