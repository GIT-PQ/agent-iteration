# 3.1 问题归因（工件只读）

## 目标

回答两个问题：这次失败归谁的责任（五类问题），以及为什么发生（根本原因 vs 直接诱因）。归因没做扎实就改代码，改的是最后一个处理节点而不是病灶。

## 输入

用户反馈、失败产物、执行轨迹（轨迹留在执行平台，需要时向用户索取）。

## 活动

### 1. 归类五类问题（可多选，每项给理由和证据）

| 问题类型 | 典型表现 | 主要责任层 |
|---|---|---|
| 工件设计问题 | 指令缺失、职责冲突、步骤顺序不合理 | SKILL.md、Agent 流程或架构 |
| 脚本实现问题 | 结构被破坏、重复输出、校验失效 | 确定性脚本或共享组件 |
| Agent 执行问题 | 跳过步骤、误读报告、临时修补产物 | 执行约束、轨迹审核或提示 |
| 输入材料问题 | 缺失、矛盾、OCR 污染、无法确定事实 | 材料治理和异常状态 |
| 人工裁决缺失 | 多个候选都合理但无法自动确定 | 人机交互和暂停条件 |

### 2. 分离根因

同一问题可能含两层原因（例如工件设计先破坏结构，Agent 又用临时补丁造成重复）。分别记录：

- **根本原因**：为什么进入错误状态
- **直接诱因**：为什么本次表现为当前错误

不要只根据最终现象修改最后一个处理节点。

## 向原始 Agent 提问（平台交接）

失败发生在别的执行平台、且原始 Agent 会话仍可问时：

1. 打开 `assets/templates/01-归因提问模板.md`，把失败现象（用户反馈原文、失败产物描述、预期与实际差异）填进 `{{失败现象}}` 槽位。
2. 把整段提问 prompt 交给用户，请其贴到执行平台对话。
3. **停下等待**——这是人工澄清等待态，不要替平台 Agent 编造回答。
4. 回答贴回后，按 `assets/templates/01-归因问答记录模板.md` 落盘到 `iterations/{任务编号}/01-归因问答.md`：提问内容与平台回答同文件，回答原样 copy 不改一字。

若轨迹和失败产物在本地可得（用户直接提供了会话记录、日志），跳过平台往返，直接归因。不确定项如实标注"不知道"，不要补全。

## 复核

归因结论需要复核（迭代侧 Agent 或人）：确认 / 改判（写明依据）/ 补充证据。复核意见只追加在 `01-归因问答.md` 的 `## 复核意见` 下，不修改上文。整体作废重问时另存 `01-归因问答-v2.md`，旧文件保留作废记录——编号 01 标识状态，重问只加版本后缀，不占用其他状态编号。

## 出口守卫

- 根因已分类且有证据 → 进入 3.2 变更设计
- 信息不足 → 人工澄清等待态，裁决事件到达后重入归因
