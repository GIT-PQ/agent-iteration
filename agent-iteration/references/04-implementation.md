# 3.4 修改实现（唯一可写窗口）

## 目标

把 3.2 的意图层方案落成代码，改动范围不越出触及清单，一次只修一个根因。

## 输入

02-变更方案（执行依据）、基线、eval。

## 活动顺序

### 1. 执行方案

按 02-变更方案直接实施，**不重新推演影响面、不重新选层**——那些判断 3.2 已经做完。越出触及清单或方案不可行时，不擅自改方案，如实记入偏离记录并上报，等设计侧裁决。

### 2. 最小修改（内循环）

```
执行方案 → 最小修改 → 当前失败测试未通过 → 继续最小修改
                     → 测试通过 → 记录偏离、提交候选
```

- 小步修改，一次只解决一个根因
- 不顺便清理无关代码，不增加未经确认的业务规则
- 先运行当前失败测试，再逐步扩大回归范围
- 临时修复最终产物只能用于紧急交付，不能代替对工件的正式修复

内循环的退出状态是**自检**：当前失败 eval 通过 + 未扩大的回归范围通过。自检是快速失败闸，不是验证——出口判定由 3.5 的非实现者执行。

### 3. 记录偏离

`iterations/{任务编号}/04-变更记录.md`（模板：`assets/templates/04-变更记录模板.md`）只记三样：

- **候选版本指针**：commit hash
- **自检退出状态**：跑了哪条当前失败 eval、回归范围跑了 N 条/未扩大
- **偏离记录**（无偏离写"无"）：方案不可行 / 越出触及清单 / 临时补救 / 人工裁决——每条写发生了什么、怎么处理、依据

"改了什么"由 git diff 承载，"为什么改"由 02-变更方案承载，"改得对不对"由 3.5 承载——本文件只记偏离和指针。

## git 提交规范

commit 与 tag 分工：**commit 是检查点，tag 是定稿**。

- **提交时机**：本状态出口——自检通过后、送独立验证前。候选必须以 commit 为冻结实体（工作区冻不住，hash 才不可变），验证对象 = 提交对象，零缝隙。
- **commit message**：`[任务编号] 摘要`（如 `[T-003] 修复华东区重复输出`），与迭代日志双向索引。
- **失败候选**：留在历史中，是重试证据；介意主线干净可用任务分支，发布时合并回主线。

## 出口守卫

候选已 commit、工件冻结 → 进入 3.5 验证回归。提交后修改窗口关闭；需要改即走 3.5 的回跳边解冻重做。
