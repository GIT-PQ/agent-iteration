# 3.3 测试准备（工件只读）

## 目标

没有基线，只能证明新版本能运行，无法证明它比旧版本更好，也无法发现修复一处却破坏另一处。没有 eval，失败无法复现，验证就退化为"看着挺对"。

## 输入

失败样本、旧版本工件。

## 活动顺序

### 1. 保存旧版本基线

写入 `results/{eval_id}/{版本}/`：

- 修改前的工件版本（Git 提交或快照）
- 相同测试输入下的旧输出
- 断言和人工审核结果
- token、运行时长等指标（运行轨迹留在平台，不入基线——基线只能存输出）

### 2. 将失败转成 eval

每个失败案例/回归项在 `evals/` 下新建一个 JSON 文件，文件名即 `{eval-id}.json`，测试输入放 `evals/files/`。骨架见 `assets/templates/03-eval模板.md`：

```json
{
  "id": "stable-test-id",
  "task": "T-001",
  "criteria": ["S1", "I2"],
  "prompt": "真实但去业务化的用户请求",
  "expected_output": "人可理解的成功标准",
  "files": ["evals/files/input.ext"],
  "assertions": [
    "输出文件可打开",
    "关键字段仅出现一次",
    "禁止内容不存在"
  ]
}
```

`task` 与 `criteria` 字段建立 eval 与任务、验收标准的双向溯源：02-验收标准的「对应 eval」列回填本文件的 id。

**断言必须落实为可执行检查**（脚本断言或 grader rubric），否则只是看起来像测试的注释。人工层的验收标准不转 eval，留在 02 由人裁决。

### 3. 写测试准备记录

`iterations/{任务编号}/03-测试准备.md`（模板：`assets/templates/03-测试准备模板.md`），只放两样东西：

- **eval 清单**：本任务产出的全部 eval（id、类型修复/回归、对应标准、断言落实方式）
- **脱敏对照表**：真实信息 → 替身。eval 与测试输入中只出现替身，本表是唯一还原路径，放任务私有目录以隔离敏感信息

测试资产保留触发问题所需的结构特征，但删除真实公司名、批号、项目名、业务结论和参考答案内容。

## 防迭代过拟合

把查询分为**训练集**（允许用于分析失败和修改工件）与**验证集**（不参与修改，只检查泛化）。避免：把真实失败句子直接加入通用词典；为单个文件名或批号增加专用分支；每次只重跑同一个案例。先提炼通用结构（如"多个文本节点表达同一内容"），再用业务值不同的样本验证。

## 出口守卫

旧版本可稳定复现失败 → 进入 3.4 修改实现。复现不稳定（时好时坏）本身就是归因线索，回到 3.1 补充证据。
